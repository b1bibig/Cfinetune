## 1. 이 실험이 뭘 하려는 건지 (처음 보는 사람용)

### 1.1 MoE 모델이 뭐냐

보통 언어모델(덴스 모델)은 단어(토큰) 하나를 처리할 때 모델의 모든 가중치를 다 쓴다.
MoE(Mixture of Experts, 전문가 혼합) 모델은 층마다 "전문가"라는 작은 신경망을 여러 개 두고,
**라우터**가 토큰마다 그중 몇 개만 골라서 쓴다.

ERNIE-4.5-21B-A3B의 경우:

- 28층. 0번 층은 일반 MLP, 1~27번 층이 MoE 층
- MoE 층마다 전문가 64개, 그중 토큰마다 **6개만** 골라 씀
- 추가로 "공유 전문가" 2개는 모든 토큰이 항상 지나감
- 전체 파라미터 약 21.8B인데 토큰 하나 처리할 때 실제로 쓰는 건 약 3B (이름의 "A3B" = Active 3B)
- 전체 파라미터의 약 94%가 라우팅 전문가에 들어 있음

그래서 MoE 모델은 **"계산은 작은 모델처럼, 크기(메모리)는 큰 모델처럼"** 이라는 특징이 있다.
21B짜리를 BF16으로 올리면 약 44GB라 48GB 이상 GPU(A100 80GB, A6000 48GB 등)가 있어야 돌아가는데,
막상 토큰마다 계산하는 양은 3B 모델 수준이다. 메모리만 해결되면 빠르다는 뜻이다.

### 1.2 칼질(전문가 프루닝)이 뭘 해결하나

메모리가 문제니까, 안 쓰는 전문가를 지우면 된다는 발상이다.
그런데 "안 쓰는" 전문가는 **무슨 데이터를 넣느냐**에 따라 다르다.
영어 코딩 데이터를 넣으면 코딩 전문가가 바쁘고, 한국어를 넣으면 다른 전문가들이 바쁘다.

이 실험은 **한국어 데이터를 흘려 보내서 한국어에 중요한 전문가만 남기는** 쪽이다.
"원래 한국어를 못하는 모델인데, 그래도 한국어가 들어오면 그나마 열심히 일하는 전문가들"을 찾아서 남긴다.

- 64개 → 48개: 25% 칼질
- 64개 → 32개: 50% 칼질

중요한 점: **칼질해도 토큰당 속도는 거의 안 빨라진다.** 토큰마다 6개를 고르는 건 그대로라서 계산량이 같다.
칼질이 줄이는 건 **파일 크기와 VRAM**이다. 그래서 "더 작은(싼) GPU에 들어간다"가 칼질의 이득이다.

### 1.3 전문가가 "중요한지"는 어떻게 재나 (REAP)

01 노트북이 하는 일이다. 한국어 데이터를 모델에 흘리면서 층마다, 전문가마다 두 가지를 기록한다.

| 기준 | 뜻 |
|---|---|
| 빈도 (freq) | 이 전문가가 뽑힌 토큰 수 / 전체 토큰 수. 얼마나 자주 불려 나오나 |
| REAP 점수 | 뽑혔을 때, 라우터 가중치 g × 전문가 출력 크기 ‖f(x)‖ 의 평균. 불려 나왔을 때 결과에 얼마나 크게 기여하나 |

REAP는 Cerebras가 낸 전문가 프루닝 방법(ICLR 2026)의 중요도 식이다.
원 논문은 코딩 데이터로 쟀는데 여기서는 한국어로 잰다.

**재구성 검사**도 같이 한다. 기록한 값으로 "전문가 출력 × 가중치의 합 + 공유 전문가 출력"을 직접 계산해서
실제 모델 층 출력과 비교한다. 이게 다르면 "내가 이해한 라우팅 계산식이 모델과 다르다"는 뜻이라
그 상태로 점수를 매기면 엉뚱한 전문가를 지우게 된다. 그래서 상대오차가 0.05를 넘으면 멈추게 돼 있다.

오늘 결과: **재구성 오차 최대 0.0031.** 기준(0.05)보다 16배 작다. 계산식이 모델과 맞는다는 뜻이다.

### 1.4 양자화

가중치를 16비트(BF16) 대신 더 적은 비트로 저장하는 것.
llama.cpp의 GGUF 형식을 쓰고, 비트 수에 따라 이름이 붙는다.

| 형식 | 가중치당 비트 (오늘 실측) | 원본 21.8B 기준 크기 (오늘 실측) |
|---|---|---|
| BF16 | 16 | 약 44GB (43.7G, 변환 로그) |
| Q8_0 | 8.50 | 22,128 MiB (약 23.2GB) |
| Q6_K | 6.57 | 17,088 MiB → 파일 **17.92GB** |
| Q4_K_M | 4.85 | 12,630 MiB → 파일 **13.25GB** |
| Q3_K_M | 약 3.9 | (ko-k32에서만 만듦) |
| Q2_K | 약 3.0 | (ko-k32에서만 만듦) |

변환 순서는 모든 변형이 같다: HF 체크포인트 → **Q8_0** GGUF → 원하는 형식으로 다시 양자화.
중간에 Q8_0을 거치는 이유는 "같은 절차"로 통제 변인을 맞추기 위해서다 (방법론 6절).

Q6_K는 거의 무손실이라 **칼질 효과를 비교하는 기준 정밀도**로 쓰고,
Q4_K_M은 실제 배포용 형식이라 **경제성 비교**에 쓴다. 원본도 Q4_K_M을 따로 만들어서 공정하게 비교한다.

오늘 본 숫자 하나: 원본 Q6_K가 17.92GB라 **L4(24GB)에 들어간다.** 그래서 02는 L4 한 종류로 모든 변형을 같은 GPU에서 잴 수 있다.

### 1.5 어휘 확장 + LoRA (03, 아직 안 함)

ERNIE는 영어·중국어 모델이라 한국어 글자가 어휘에 거의 없다.
"녕", "답" 같은 흔한 글자도 UTF-8 바이트 3개로 쪼개서 읽는다. 같은 한국어 문장을 gpt-oss는 25토큰, ERNIE는 39토큰으로 쪼갠다.

토큰이 많으면:
- 같은 글을 처리하는 데 계산을 더 한다 (느리고 전기를 더 씀)
- 문맥 길이를 더 빨리 다 쓴다
- 모델이 "글자"를 바이트 조각으로 조립해야 해서 한국어를 더 못한다

그래서 03에서 한국어 토큰 8,000개를 어휘에 덧붙인다 (위키 기준 토큰 수 약 39% 감소).
새로 붙인 토큰은 처음에 의미를 모르니까 학습이 필요하다:

1. **1단계:** 모델은 얼려두고 **새 토큰의 임베딩만** 한국어 위키로 학습 (기본 2천만 토큰)
2. **2단계:** 한국어 대화 6,000개로 LoRA 학습 (어텐션 + 공유 전문가 + 남은 전문가 + 새 임베딩, 라우터는 고정)

LoRA는 원래 가중치는 그대로 두고 옆에 작은 행렬(랭크 16)을 붙여서 그것만 학습하는 방법이다.
학습 후 원래 가중치에 합쳐서(merge) 다시 GGUF로 만든다.

### 1.6 최종 목표 (가설)

> 원본(BF16, A100 80GB 필요)보다 **한국어를 더 잘하면서**, T4·L4 같은 **작은 GPU에서 더 빠르고 싸게** 도는 모델.

- 칼질 → 작은 GPU에 들어감 (크기)
- 양자화 → 더 작아지고, 메모리에서 읽을 데이터가 줄어 빨라짐
- 어휘 확장 → 같은 한국어를 더 적은 토큰으로 → 글자 기준으로 빨라지고 에너지·비용 감소
- LoRA → 칼질로 잃은 능력 보충 + 한국어 능력 향상

결과는 마지막에 Qwen3.8-Flash-Next(약 180B)에 계산으로 확장해서 "같은 비율이면 48GB GPU 1장에 들어간다"까지 보이는 게 목표다.

## 3. 막힌 곳과 해결 (자세히)

### 3.1 크롬 계정에 유닛이 0개

지침의 "시작 전 확인 4번"에 걸렸다. 크롬에는 계정이 하나뿐이었고 그 계정은 컴퓨팅 단위가 0이었다.
지침대로 아무것도 실행하지 않고 멈췄다. 유닛은 다른 Workspace 계정에 있었다.

비밀번호 입력은 에이전트가 하지 않는다 (안전 규칙: 다른 서비스에 비밀번호를 쳐서 로그인하지 않음).
사용자가 밖에 있어서 사용자 쪽 다른 에이전트가 파이어폭스로 로그인했고,
이쪽 에이전트는 **그 파이어폭스 프로필을 복사**해서 원격 제어 가능한 파이어폭스를 하나 더 띄워 이어받았다.

- 원래 파이어폭스는 원격 제어 포트 없이 떠 있어서 조종할 수 없었다.
- 복사본은 `-no-remote -profile <복사본> --remote-debugging-port 9333`으로 띄우고
  puppeteer-core의 WebDriver BiDi로 붙었다.
- 구글은 여러 계정이 로그인돼 있으면 `authuser=` 번호로 고른다. 이 계정은 7번째(`authuser=6`).
  코랩 주소 뒤에 `?authuser=6`을 붙여서 열었다.

**교훈:** 유닛이 있는 계정을 미리 크롬(또는 에이전트가 조종하는 브라우저)에 넣어두면 이 단계가 통째로 사라진다.

### 3.2 드라이브 연결 권한 + 타임아웃

01 두 번째 셀이 `drive.mount()`를 하면 "Google Drive for desktop"이라는 OAuth 창이 뜨고
드라이브 파일 보기·수정·삭제, 구글 포토, 구글 서비스 메시지 조회 등 권한 7~8개를 "모두 선택"으로 달라고 한다.
코랩 드라이브 마운트의 기본 절차이고 지침에도 "모두 허용"으로 돼 있지만,
범위가 넓어서 에이전트 쪽 안전장치가 사용자 확인을 요구했다.
확인을 받는 데 약 30분이 걸렸고, 그 사이 코랩 쪽 마운트가 기다리다 `ValueError: mount failed`로 끝났다.

이 30분 동안 **A100 런타임이 켜진 채 놀았다.** 유닛 손실 약 2~3개로 추정.

해결: 권한 허용 후 마운트 셀부터 다시 실행(`셀 및 하위 셀 실행`). 두 번째에는 바로 마운트됐다.

**교훈:** 권한 범위가 넓은 OAuth는 에이전트가 멈추고 묻는다. 사용자가 그 자리에서 답할 수 있을 때 돌리거나,
지침에 "드라이브 권한은 미리 승인함"이라고 적어두고 사용자가 시작할 때 한 번 말해 두면 좋다.

### 3.3 A100이 40GB로 배정됨

코랩의 "A100 GPU"는 40GB와 80GB 두 종류가 섞여 있다. 런타임 유형 창에는 40/80을 고르는 옵션이 없었다.
첫 배정은 `NVIDIA A100-SXM4-40GB, 40960 MiB`. 노트북의 GPU 확인 셀이 `assert mem >= 50`으로 막았다
(원본 BF16이 44GB라 40GB에는 안 들어간다).

지침대로 런타임 삭제 후 재시도할 때, 사용자가 **"고용량 RAM" 토글**을 켜보라고 했고, 켜니까 바로
`NVIDIA A100-SXM4-80GB, 81920 MiB`가 배정됐다. 01을 다시 돌릴 때도 처음부터 켜고 시작했더니 한 번에 80GB.

두 번 다 그랬으니 우연일 수도 있지만, **A100 + 고용량 RAM = 80GB** 경향은 있어 보인다.
(코랩은 고용량 RAM일 때 더 큰 머신 타입을 주는데, 80GB A100은 시스템 RAM이 큰 머신에 붙어 있는 것으로 보인다. 추정.)

**교훈:** 지침 1단계 2번에 "고용량 RAM 켜기"를 넣으면 40GB 재시도가 줄어들 것이다.

참고로 L4는 고용량 RAM이 강제로 켜져 있다 (토글이 회색으로 잠김).

### 3.4 01 칼리브레이션 에러: `NonMatchingSplitsSizesError`

에러 메시지 (요약):

```
File "src/cfinetune/data.py", line 142, in sft_examples
    ds = load_dataset(name, data_files=file, split="train") if file else load_dataset(name, split="train")
...
datasets.exceptions.NonMatchingSplitsSizesError:
  [{'expected': SplitInfo(name='train', num_bytes=3880686436, num_examples=460281),
    'recorded': SplitInfo(name='train', num_bytes=480798317, num_examples=57536, dataset_name='smol-koreantalk')}]
```

무슨 일이었나:

1. 설정(`configs/experiment.yaml`)은 smol-koreantalk 8개 파일 중 **첫 파일만** 쓰도록 돼 있다:
   `file: data/train-00000-of-00008.parquet`
2. `load_dataset(..., data_files=첫 파일)`이 그 파일(244MB, 57,536개)만 받아서 `train` 분할을 만들었다.
3. 그런데 `datasets` 라이브러리는 데이터셋 저장소 README에 적힌 **전체** `train` 크기(460,281개, 3.88GB)와 비교해서
   "크기가 안 맞는다"며 에러를 냈다. `Generating train split: 13% 57536/460281`이 그 흔적이다.
4. 같은 방식으로 위키백과 한 파일을 읽는 부분은 통과했는데, 위키 쪽(`_wiki_articles`)은 `streaming=True`로 읽어서
   분할 크기 검사를 아예 안 하기 때문이다.

고친 것 (커밋 `aea2fe8`):

```python
ds = load_dataset(name, data_files=file, split="train", verification_mode="no_checks") if file else load_dataset(name, split="train")
```

`data_files`로 일부 파일만 지정할 때만 검사를 끈다. 전체를 받을 때(`file` 없음)는 그대로 검사한다.

**왜 전체(8개 파일)를 받지 않고 1/8만 쓰나** — 사용자가 물어서 정리한 답:

- **양이 충분하다.** 01에 필요한 대화 데이터는 512토큰 조각 256개(칼리브레이션 전체 512조각 중 절반), 약 13만 토큰.
  대화로 치면 1천 개 안쪽. 첫 파일에는 5만 7천 개가 있고, 앞 2만 개를 건너뛰어도 3만 7천 개가 남는다.
- **전체는 손해다.** 8개 다 받으면 3.9GB. 받고 분할을 만드는 데 몇 분씩 걸리고, 그동안 A100 유닛이 나간다.
  첫 파일 하나는 244MB라 30초 안에 끝났다.
- **겹침 방지가 이 구조에 묶여 있다.** 03의 LoRA 학습도 같은 첫 파일에서 (같은 시드로 섞은 순서의) **앞쪽 6천 개**를 쓰고,
  01은 **2만 번째부터** 쓴다. 그래서 "칼질 기준 데이터"와 "학습 데이터"가 안 겹친다.
  01만 전체 데이터로 바꾸면 섞는 순서가 달라져서 이 보장이 깨진다.
- 같은 함수(`sft_examples`)를 03 LoRA에서도 쓰므로, 이 수정이 없었으면 03에서도 같은 에러가 났을 것이다.

### 3.5 "선택" 측정을 중간에 끊는 방법 (코랩의 실행 대기열)

01의 뒷부분 "(선택) 원본 BF16의 속도·전력 측정"은 llama.cpp 빌드(15분) + BF16 GGUF 변환(10~20분) + 벤치로 약 45분, 약 6유닛이다.
02가 쓰는 건 `stats-ko.json`뿐이고 llama.cpp는 02가 L4에서 알아서 빌드하므로 사용자가 이번엔 건너뛰기로 했다.

문제는 이미 "모두 실행"으로 셀들이 대기열에 들어가 있었다는 것.
코랩의 **실행 중단**(`런타임 → 실행 중단`, Ctrl+M I)은 **지금 도는 셀 하나만** 멈추고, 대기열의 다음 셀은 계속 실행한다.

그래서 실제로는:

1. 빌드 셀 중단 → 다음 셀(BF16 변환)이 바로 시작됨
2. 변환 셀 중단 → 다음 셀(벤치 부분)은 llama-bench가 없어서 바로 에러, 그다음 **마지막 셀(AUTO_OFF)** 이 실행됨
3. 마지막 셀이 `push_results()`(드라이브 저장) 후 `runtime.unassign()`으로 런타임을 끔

결과적으로 원하는 대로 됐지만, 의도적으로 하려면: 중단하고 싶은 지점의 다음 셀들을 하나씩 중단하거나,
처음부터 "모두 실행" 대신 원하는 셀까지만 실행하고 마지막 셀만 따로 실행하면 된다.

### 3.6 빌드가 지침보다 느림

02의 llama.cpp 빌드가 13:17 → 13:45, **약 28분** 걸렸다 (지침: 10~15분).
L4 런타임은 CPU 코어가 적은 머신이라 CUDA 커널(템플릿 인스턴스 수백 개) 컴파일이 오래 걸린다.
빌드 결과는 드라이브 `cfinetune/cache`에 저장되니까 **다음 노트북부터는 복사만 한다.**
(01에서 빌드를 끝까지 했으면 A100 머신에서 더 빨리 빌드됐겠지만, 그 머신 시간이 시간당 5유닛이라 L4에서 빌드하는 게 싸다.)

- Q1: 48개까지는 거의 유지, 32개에서는 눈에 띄게 떨어짐
- Q2: 4비트까지는 거의 유지, 2비트에서 크게 떨어짐

### 변형마다 하는 일

1. `02_prune.py`: (칼질 변형만) `stats-ko.json`의 REAP 점수로 층마다 상위 K개만 남긴 HF 체크포인트를 만든다.
   GPU가 필요 없다. 남은 전문가의 가중치는 원본과 비트 단위로 같고, 라우터 가중치·보정값도 같은 전문가만 남긴다.
2. `03_make_gguf.py`: Q8_0 GGUF로 변환 후 각 형식으로 다시 양자화.
3. `05_eval.py`: 객관식 3,008문항 + 퍼플렉시티.

   - 채점: 채팅 형식으로 문제를 주고 답변 자리에 "정답:"까지 써둔 뒤, 다음 토큰으로 A~E 중 확률이 가장 높은 것을 답으로 봄
   - 퍼플렉시티: 한국어/영어 위키 (칼리브레이션에 안 쓴 파일), `PPL[ko] = …, 글자당 비트 …` 출력
4. `06_bench.py`: llama-bench로 프롬프트 처리 512토큰 / 생성 128토큰 속도 10번씩, nvidia-smi로 0.2초마다 전력.
   그리고 `configs/gen_prompts.txt`의 한국어 질문 8개에 실제로 답하게 해서 **답변 1개당 Wh, 1000글자당 Wh**.
5. 드라이브에 `results/eval/<이름>.json`, `results/bench/<이름>@L4.json` 저장.

02는 **끝난 변형을 건너뛴다** (`results/eval/<이름>.json`과 `results/bench/<이름>@*.json`이 둘 다 있으면).
그래서 런타임이 끊겨도 처음부터 다시 실행하면 남은 변형만 이어서 한다. 처음 20~30분은 원본을 다시 받는다.

### 오늘 관찰한 것 (02 진행 중)

- 원본 Q6_K 양자화 7분 15초(`434521 ms`), Q4_K_M도 비슷.
- 객관식 평가는 L4에서 1분에 약 600문항 → 3,008문항이 5~6분.
- 평가 시작 직후 `Token indices sequence length is longer than the specified maximum sequence length for this model (279185 > 131072)` 경고가 한 번 뜬다.
  퍼플렉시티용 위키 텍스트(30만 글자)를 한 번에 토큰화할 때 HF 토크나이저가 내는 경고이고,
  실제로는 512토큰 조각으로 잘라서 모델에 넣으므로 문제 아닐 것으로 본다. PPL 값이 정상 범위로 나오는지 확인 예정.

## 6. 03 계획: 1단계 2천만 토큰 전부 학습

### 원래 설정

```yaml
stage1:
  n_tokens: 20000000   # 최대치. 03 노트북이 시범 학습 속도로 hours 안에 끝나게 줄임
  hours: 3             # 1단계에 쓸 시간 (A100 40GB 시간당 약 5.4유닛)
```

03 노트북은 먼저 시범으로 1단계·2단계를 5스텝씩 돌려 속도와 최대 VRAM을 잰 다음,

```python
STAGE1_TOKENS = min(n_tokens, 초당토큰 × 3600 × hours)   # 100만 단위로 내림
```

으로 1단계 학습량을 정하고 드라이브(`ckpt/stage1_tokens.json`)에 저장한다. 끊겨서 다시 할 때도 같은 값을 쓴다.
즉 **3시간은 기술적인 이유가 아니라 예산 상한**이었다. 3시간이면 약 16유닛.

### 바꾼 것 (커밋 `58a2822`)

```yaml
stage1:
  n_tokens: 20000000   # 이만큼 다 학습 (hours 안에 안 끝나는 속도일 때만 줄임)
  hours: 8             # 안전 상한 (A100 40GB 시간당 약 5.4유닛)
```

사용자 결정: 2천만 토큰을 다 학습시키는 방향.
8시간 안에 2천만 토큰이 되는 속도면 다 하고, 그보다 느린 경우에만 줄어든다.

왜 이게 의미 있나:
- 1단계는 모델을 얼리고 **새 한국어 토큰 8,000개의 임베딩만** 학습한다.
- 새 토큰 임베딩은 처음에 "원래 조각(바이트)들의 평균"으로 초기화된다. 학습이 모자라면 새 토큰이 원래 바이트 조합보다 오히려 의미가 흐릿해서,
  어휘를 넣기 전보다 한국어가 어색해질 수 있다.
- 방법론 9절도 "드물게 나오는 새 토큰은 충분히 배우지 못할 수 있다"를 한계로 적어 두었다.
- 2천만 토큰이면 새 토큰 하나당 평균 노출 횟수가 3시간 상한보다 늘어난다 (속도에 따라 다름).

비용: 1단계가 3시간을 넘기는 만큼 시간당 약 5.4유닛씩 더 든다. 100유닛이 들어오면 감당 가능.

시범 학습이 이런 줄을 출력하니까, 03 돌릴 때 이 숫자를 보고 판단하면 된다:

```
최대 VRAM xx.x GB / 1단계 초당 n 토큰 -> 20,000,000 토큰 (약 x.x시간) / 2단계 약 x.x시간
```

노트북 03의 설명 문구엔 아직 "기본 3시간"이라고 적혀 있는데 동작에는 영향이 없다.

## 7. `agent_colab.md`에 반영하면 좋을 것 (오늘 겪은 것 기준)

1. **시작 전 확인**: 유닛 있는 계정이 에이전트가 조종하는 브라우저에 로그인돼 있는지. 여러 계정이면 `?authuser=N`.
2. **1단계 2번**: A100 고를 때 **고용량 RAM 켜기** (80GB 배정 확률↑, 오늘 2/2).
3. **드라이브 권한**: "Google Drive for desktop" 권한 창에서 체크박스가 7~8개 나오고 "모두 선택" 후 계속. 오래 두면 마운트가 타임아웃되니 바로 처리.
   타임아웃(`ValueError: mount failed`)은 코드 에러가 아니므로 마운트 셀부터 한 번 다시 실행해도 된다.
4. **01 선택 측정 건너뛰기**: 건너뛸 거면 "모두 실행" 대신 그래프 셀까지만 실행하고 마지막 셀(AUTO_OFF)을 따로 실행.
   이미 모두 실행했다면 중단을 셀마다 해야 한다 (코랩 실행 중단은 지금 셀만 멈춤).
5. **빌드 시간**: L4에서 llama.cpp 첫 빌드는 25~30분 걸릴 수 있다 (지침은 10~15분).

## 9. 용어 정리

| 용어 | 뜻 |
|---|---|
| MoE | 층마다 전문가 여러 개 중 일부만 골라 쓰는 구조 |
| 전문가 (expert) | MoE 층 안의 작은 MLP. ERNIE는 층마다 64개 |
| 라우터 (router) | 토큰마다 어느 전문가를 쓸지 고르는 작은 층 |
| 공유 전문가 | 라우터와 상관없이 모든 토큰이 지나가는 전문가 (ERNIE는 2개) |
| 칼질 / 프루닝 | 덜 중요한 전문가를 지워서 모델을 작게 만드는 것 |
| REAP | 라우터 가중치 × 전문가 출력 크기로 전문가 중요도를 재는 식 |
| 칼리브레이션 | 데이터를 흘려 보내며 통계(여기서는 전문가 점수)를 재는 단계 |
| 양자화 | 가중치를 더 적은 비트로 저장 |
| GGUF | llama.cpp의 모델 파일 형식 |
| Q6_K, Q4_K_M … | GGUF 양자화 형식 이름. 숫자가 대략 비트 수 |
| BPW | bits per weight, 가중치 하나당 평균 비트 |
| LoRA | 원래 가중치 옆에 작은 저랭크 행렬을 붙여 그것만 학습하는 방법 |
| 어휘 확장 | 토크나이저에 새 토큰을 추가하고 임베딩을 학습 |
| 퍼플렉시티 (PPL) | 모델이 다음 토큰을 얼마나 헷갈려하나. 낮을수록 좋음 |
| 글자당 비트 (bpc) | 어휘가 다른 모델끼리 비교하려고 글자 단위로 환산한 손실 |

| MMLU | 영어 지식 객관식 |
