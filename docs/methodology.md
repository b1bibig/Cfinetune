# 탐구 방법론: MoE 언어모델의 한국어 특화 경량화와 경제성 분석

## 1. 탐구 질문과 가설

| 번호 | 질문 | 가설 |
|---|---|---|
| Q1 | 한국어 데이터로 전문가를 고르면, 영어 데이터로 고를 때보다 한국어 성능을 더 잘 지킬까? | 한국어 보정이 같은 개수 기준 한국어 점수가 더 높고, 대신 영어 점수는 더 떨어진다 |
| Q2 | 전문가를 얼마나 줄여도 될까? (32 → 24 → 16개) | 24개까지는 한국어 성능이 크게 유지되고, 16개에서는 눈에 띄게 떨어진다 |
| Q3 | 양자화 형식에 따라 손실이 어떻게 다를까? | 원본 형식(MXFP4)은 손실이 없고, 같은 4비트라도 다른 형식(Q4_0)은 손실이 생긴다 |
| Q4 | 저랭크 추가학습(LoRA)으로 한국어 성능을 회복·향상할 수 있을까? | 문장 자연스러움과 한국어 이해 점수는 오르지만, 전문 지식 점수(KMMLU)는 조금만 오른다 |
| Q5 | 경량화하면 비용과 에너지가 얼마나 줄까? 더 큰 모델(Qwen3.8-Flash-Next)에는? | 파일 크기와 필요 GPU 등급이 줄어 시간당 비용이 크게 줄고, 같은 비율을 적용하면 Flash-Next도 48GB GPU 1장에 들어간다 |

## 2. 대상 모델: gpt-oss-20b

| 항목 | 값 |
|---|---|
| 구조 | MoE (Mixture of Experts), 24층 |
| 전문가 | 층마다 32개 중 4개 선택 (공유 전문가 없음) |
| 파라미터 | 전체 21B, 토큰당 3.6B 사용. 이 중 전문가가 약 19B (약 90%) |
| 배포 형식 | 전문가는 MXFP4(4비트), 나머지(어텐션·임베딩·라우터)는 BF16 |
| 라이선스 | Apache 2.0 |
| 한국어 | 공식 지원 언어가 아님 (영어 중심) |

고른 이유:
- 베이스 성능이 좋고, 한국어 특화 모델이 아니라서 "한국어 특화로 바꾸기"를 보여주기 좋다.
- 전문가가 전체의 90%라 전문가를 줄이면 크기가 크게 줄어든다.
- **학습 단계부터 4비트(MXFP4)를 전제로 만들어져서**, 원본 4비트 블록을 그대로 잘라 옮기면 프루닝을 **손실 없이** 할 수 있다. 그래서 프루닝 효과와 양자화 효과를 깔끔하게 분리할 수 있다.

최종 적용 대상인 Qwen3.8-Flash-Next(약 180B)는 코랩에서 직접 실험할 수 없어서, 같은 MoE 구조인 gpt-oss-20b로 방법을 검증하고 결과를 Flash-Next 사양에 대입해 경제성을 계산한다.

## 3. 파이프라인

```
 [원본 gpt-oss-20b (MXFP4, 13GB)]
        │
        ├─① 전문가 중요도 측정 ── 한국어 위키 / 영어 위키를 흘려 보내며 층별·전문가별 점수 기록
        │        (A100 80GB)        → stats-ko.json, stats-en.json
        │
        ├─② 프루닝 ────────────── 층마다 점수 상위 K개만 남기고 잘라냄 (K = 24, 16)
        │        (CPU)              MXFP4 블록을 그대로 옮기므로 남은 전문가는 원본과 비트 단위로 같음
        │
        ├─③ 양자화 ────────────── GGUF 변환 후 MXFP4_MOE / Q8_0 / Q4_0 비교
        │        (CPU)
        │
        ├─④ 저랭크 추가학습 ───── 한국어 지시문 6천 개로 LoRA → 합치기 → 다시 4비트로
        │        (A100 40GB)
        │
        └─⑤ 평가 + ⑥ 측정 ─────── 모든 변형을 같은 엔진(llama.cpp), 같은 GPU(L4)로
                 (L4)               한국어/영어 객관식, 퍼플렉시티, 속도, 전력, 메모리
                        │
                        └─⑦ 경제성 분석 ── 100만 토큰당 비용, 1000토큰당 에너지, 필요한 GPU
                                           + Qwen3.8-Flash-Next 확장 계산
```

## 4. 단계별 방법

### 4.1 전문가 중요도 측정 (`scripts/01_calibrate.py`)

보정 데이터 x가 지나갈 때, 층마다 라우터가 고른 전문가 j에 대해 다음을 기록한다.

- 라우터: 로짓 = xWᵀ + b, 상위 4개를 고른 뒤 그 4개에 softmax → 게이트 값 g_j(x)
- 전문가 출력 크기: ‖f_j(x)‖₂

두 가지 점수를 만든다.

| 기준 | 식 | 의미 |
|---|---|---|
| 빈도 (freq) | 전문가 j가 뽑힌 토큰 수 / 전체 토큰 수 | 얼마나 자주 쓰이나 |
| REAP | (1/뽑힌 토큰 수) × Σ g_j(x)·‖f_j(x)‖₂ | 뽑혔을 때 출력에 얼마나 크게 기여하나 (Cerebras REAP, 2025) |

- 보정 데이터: 한국어 위키 또는 영어 위키, 512토큰 × 512조각 (약 26만 토큰)
- **재구성 검사:** 우리가 직접 계산한 Σ g·f 가 실제 모델 출력과 같은지 확인한다(상대오차 < 5%). 다르면 계산식이 틀린 것이므로 멈춘다.

### 4.2 프루닝 (`scripts/02_prune.py`)

- 층마다 점수 상위 K개를 남긴다. 모든 층에서 K는 같다(모델 설정의 전문가 수가 하나이기 때문).
- gpt-oss의 전문가 관련 텐서는 모두 0번 축이 전문가 축이라, 0번 축에서 남길 번호만 고르면 된다.
- 라우터는 고른 4개에만 softmax를 하므로, 전문가를 지워도 따로 재정규화할 필요가 없다.
- 원본 MXFP4 블록·스케일을 그대로 옮기므로 **프루닝 자체에는 수치 손실이 없다.** 성능 변화는 순수하게 "전문가를 지운 효과"다.
- 검증: 한 번도 선택되지 않는 전문가만 지우면 출력이 원본과 완전히 같아야 한다 (`tests/test_pipeline.py`).

### 4.3 양자화 (`scripts/03_make_gguf.py`)

| 형식 | 전문가 | 나머지 | 비고 |
|---|---|---|---|
| 변환만 | MXFP4 (원본 그대로) | BF16 | 손실 없음. 프루닝 비교에 사용 |
| MXFP4_MOE | MXFP4 | Q8_0 | 배포용 |
| Q8_0 | Q8_0 | Q8_0 | 8비트 |
| Q4_0 | Q4_0 | Q4_0 | MXFP4와 같은 4비트지만 형식이 다름 |

**발견한 구조적 한계:** gpt-oss의 행렬 크기 2880은 256으로 나누어떨어지지 않는다. 그래서 llama.cpp의 K-양자화(Q2_K, Q3_K, Q4_K 등 256 단위 블록)는 자동으로 Q4_0, Q5_0 같은 32 단위 형식으로 대체된다. 즉 gpt-oss의 전문가는 llama.cpp에서 약 4비트보다 더 줄이기 어렵다. 그래서 이 모델은 비트 수를 줄이기보다 **전문가 수를 줄이는 것(프루닝)이 크기를 줄이는 주된 방법**이 된다.

### 4.4 저랭크 추가학습 (`scripts/04_train_lora.py`)

| 항목 | 값 |
|---|---|
| 대상 | ko-reap-k16 (한국어 보정, 전문가 16개) |
| 데이터 | KULLM-v2 (한국어 지시문, Apache 2.0)에서 6,000개 |
| 형식 | gpt-oss 채팅 형식(harmony), 답변(final 채널)에만 손실 |
| LoRA 위치 | 어텐션 q/k/v/o + 남은 전문가의 gate_up_proj, down_proj |
| 고정 | 라우터 (프루닝으로 정한 선택 구조 유지), 임베딩 |
| 설정 | r=16, α=32, 학습률 2e-4(cosine), 1에폭, 최대 1024토큰, 배치 2×8 |
| 이후 | LoRA를 모델에 합침 → BF16 → GGUF → MXFP4_MOE로 다시 양자화 |

합친 뒤에는 값이 원래의 4비트 격자에서 벗어나므로, 재양자화 손실을 Q8_0 버전과 비교해 따로 확인한다.

### 4.5 평가 (`scripts/05_eval.py`)

모든 변형을 **같은 엔진(llama.cpp)·같은 프롬프트·같은 문항**으로 평가한다.

| 평가 | 내용 | 문항 수 |
|---|---|---|
| KMMLU | 한국어 전문 지식 (45과목에서 과목당 20문항) | 900 |
| HAE-RAE Bench 1.0 | 한국 문화·어휘·역사·독해 (전체) | 1,538 |
| MMLU | 영어 지식 (57과목에서 과목당 10문항). 영어 능력이 얼마나 줄었는지 확인 | 570 |
| 퍼플렉시티 | 한국어/영어 위키 (보정에 안 쓴 파일), 512토큰 × 200조각 | - |
| 생성 예시 | 에너지 분야 포함 한국어 질문 8개 | - |

**채점 방식:** 채팅 형식으로 문제를 주고, 답변 채널을 미리 열어 둔 뒤 "정답:" 다음에 올 토큰 중 보기 알파벳(A~E)의 확률을 비교해 가장 높은 것을 답으로 본다. 생각(추론) 과정을 건너뛰므로 절대 점수는 실제 사용 때보다 낮을 수 있지만, 모든 변형에 같은 방식을 쓰므로 **변형끼리 비교**하는 데는 공정하다.

### 4.6 속도·전력 측정과 경제성 (`scripts/06_bench.py`, `scripts/07_econ.py`)

- **속도:** llama-bench로 프롬프트 처리(512토큰)와 생성(128토큰)을 따로 10번씩 측정
- **전력:** 측정하는 동안 nvidia-smi로 0.2초마다 GPU 전력을 기록. 모델을 불러오는 동안처럼 GPU가 쉬는 구간은 빼고, 실제 연산 구간만 평균
- **메모리:** 파일 크기, 측정 중 최대 VRAM

| 지표 | 계산식 |
|---|---|
| 1000토큰 생성 에너지 (Wh) | 생성 중 평균 전력(W) ÷ 생성 속도(토큰/초) × 1000 ÷ 3600 |
| 100만 토큰 비용 (원) | GPU 시간당 가격 ÷ (생성 속도 × 3600) × 1,000,000 |
| 필요한 GPU | (파일 크기 + 1.5GB 여유) 이상의 VRAM을 가진 가장 싼 GPU |

GPU 가격은 코랩 컴퓨트 유닛 소모율($0.10/유닛)과 엘리스클라우드 요금을 `configs/experiment.yaml`에 넣어 계산한다.

**Qwen3.8-Flash-Next 확장:** 모델 카드 기준 라우팅 전문가 약 121B, 나머지 본체 4B, n-gram 임베딩 51B, MTP 4B로 나누고, gpt-oss에서 쓴 "남긴 전문가 비율"을 그대로 적용해 필요 메모리를 계산한다 (전문가 4.25비트, 나머지 8.5비트, n-gram 임베딩은 CPU 메모리, MTP 제외). 한국어 성능 유지율은 gpt-oss에서 측정한 값을 "예상치"로 함께 적는다.

## 8. 한계와 주의점

- 시드 하나로 한 번씩만 실험한다. 차이가 1~2%p 이내면 우연일 수 있으므로, 시간이 남으면 평가 시드를 바꿔 반복한다.
- 객관식 채점은 추론 과정을 건너뛰는 방식이라 실제 사용 성능과 다를 수 있다 (변형 간 비교용).
- 비용은 요청을 하나씩 처리하는 기준이다. 여러 요청을 묶어 처리하면 실제 비용은 더 낮아진다.
- 보정 데이터가 위키 문체라, 대화체 성능은 다르게 나올 수 있다.
- Flash-Next 확장은 계산값이다. 구조(전문가 512개, n-gram 임베딩)가 달라 실제 성능 유지율은 다를 수 있다.

## 9. 선행 연구와의 관계

| 연구 | 방법 | 이 탐구와의 차이 |
|---|---|---|
| MoE-I² (EMNLP 2024 Findings) | 층별로 다른 비율로 전문가 프루닝 + 남은 전문가 내부 저랭크 분해 | 범용 압축. 이 탐구는 **한국어 기준**으로 전문가를 고르고, 저랭크 **분해** 대신 저랭크 **추가학습(LoRA)**으로 성능을 회복 |
| REAP (Cerebras, ICLR 2026) | 라우터 가중치 × 전문가 출력 크기로 중요도 측정 후 프루닝 | 중요도 식을 그대로 사용. 원래 코딩 데이터로 보정했지만 이 탐구는 한국어/영어 보정을 비교 |
