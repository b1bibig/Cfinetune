# 탐구 방법론: 한국어를 못하는 MoE 언어모델을 칼질하고 한국어로 개조하기

## 1. 목표와 가설

**목표:** 한국어를 공식 지원하지 않는 MoE 모델(ERNIE-4.5-21B-A3B)은 BF16 약 44GB라 48GB 이상 GPU가 필요하다.
① 전문가 프루닝(칼질) → ② 한국어 어휘 확장 → ③ 한국어 추가학습(LoRA) → ④ 양자화로,
**원본보다 한국어를 잘하면서 작은 GPU(T4·L4)에서 더 빠르고 싸게 도는 모델**을 만들고, 그 경제성(비용·에너지)을 분석한다.

**어디서 무엇이 좋아지나:** MoE는 토큰마다 쓰는 전문가 수(6개)가 그대로라 칼질만으로는 토큰당 속도가 거의 안 빨라진다.
칼질은 **크기**를 줄여 작은 GPU에 들어가게 하고, 양자화는 크기와 **읽어야 할 데이터**를 줄이고,
어휘 확장은 같은 한국어를 **더 적은 토큰**(위키 기준 약 39% 적게)으로 처리하게 해서 한국어 글자 기준 속도·에너지·비용을 줄인다.

| 번호 | 질문 | 가설 |
|---|---|---|
| Q1 | 한국어 데이터로 중요한 전문가만 남기면 한국어 성능은 얼마나 떨어질까? (64 → 48 → 32개) | 48개(25% 칼질)까지는 거의 유지되고, 32개(50%)에서는 눈에 띄게 떨어진다 |
| Q2 | 양자화로 비트를 줄이면 얼마나 떨어질까? (6 → 4 → 3 → 2비트) | 4비트까지는 거의 유지, 2비트에서 크게 떨어진다 |
| Q3 | 칼질한 모델에 한국어 어휘를 넣고 한국어로 추가학습하면 원본을 넘을 수 있을까? | 한국어 이해·문장 능력(HAE-RAE, 글자당 비트)은 원본을 넘고, 전문 지식(KMMLU)은 조금만 오른다. 같은 한국어를 약 40% 적은 토큰으로 처리한다 |
| Q4 | 경량화로 비용과 에너지가 얼마나 줄까? 더 큰 모델(Qwen3.8-Flash-Next)에는? | 원본 BF16(A100 80GB) 대비 최종 모델(T4·L4)의 한국어 1000글자당 에너지와 100만 글자당 비용이 크게 줄고, 같은 비율을 적용하면 Flash-Next도 48GB GPU 1장에 들어간다 |

## 2. 대상 모델: ERNIE-4.5-21B-A3B (바이두)

| 항목 | 값 |
|---|---|
| 구조 | MoE, 28층 (0번 층은 일반 MLP, 1~27번 층이 MoE) |
| 전문가 | 층마다 64개 중 6개 선택 + 공유 전문가 2개 (항상 사용) |
| 파라미터 | 전체 약 21.8B, 토큰당 약 3B 사용. 라우팅 전문가가 약 20.4B (약 94%) |
| 배포 형식 | BF16 (약 44GB) |
| 지원 언어 | **영어, 중국어만** |
| 라이선스 | Apache 2.0 |

고른 이유:
- **한국어를 정말 못한다.** 같은 한국어 문장을 gpt-oss는 25토큰, ERNIE는 39토큰으로 쪼갠다. "녕", "답" 같은 흔한 글자도 어휘에 없어서 바이트 조각으로 읽는다. 그래서 한국어로 개조하는 효과가 크게 드러난다.
- **세 단계가 모두 의미 있다.** BF16으로 배포되고 행렬 크기(2560, 1536)가 256의 배수라 llama.cpp의 2~8비트 양자화가 모두 적용된다. 전문가가 64개라 칼질도 세밀하게 할 수 있다.
- 전문가 프루닝 연구(REAP)의 공식 코드가 지원하는 모델이다.

최종 적용 대상인 Qwen3.8-Flash-Next(약 180B)는 코랩에서 직접 실험할 수 없어서, 같은 MoE 구조인 ERNIE로 방법을 검증하고 결과를 Flash-Next 사양에 대입해 경제성을 계산한다.

```
        │
        ├─② 칼질 ─────────────── 층마다 점수 상위 48개 / 32개만 남김                       (CPU)
        │                         남은 전문가의 가중치는 원본과 비트 단위로 같음
        │
        ├─③ 양자화 ───────────── GGUF로 변환 후 Q6_K / Q4_K_M / Q3_K_M / Q2_K              (CPU)
        │
        ├─④ 한국어 LoRA ───────── 칼질한 모델(32개)을 한국어 지시문 6천 개로 추가학습        (A100 40GB)
        │                         → 합치기 → 다시 양자화
        │
        └─⑤ 평가 + 측정 ───────── 모든 변형을 같은 엔진(llama.cpp)·같은 GPU(L4)로           (L4)
                 │                한국어/영어 객관식, 퍼플렉시티, 속도, 전력, 메모리
                 └─⑥ 경제성 분석 ── 100만 토큰당 비용, 1000토큰당 에너지, 필요한 GPU
                                    + Qwen3.8-Flash-Next 확장 계산
```

## 4. 데이터: 전부 한국어, 역할별로 겹치지 않게

| 용도 | 데이터 | 양 | 비고 |
|---|---|---|---|
| ① 칼질 기준 (무엇을 남길지) | 한국어 위키백과 50% + KULLM-v2 지시문 50% (채팅 형식) | 약 26만 토큰 | 지식(문어체)과 실제 사용 형태(대화)를 함께 반영 |
| ④ LoRA 학습 (성능 올리기) | KULLM-v2 한국어 지시문 | 6,000개 | 같은 시드로 섞은 순서의 앞부분. ①은 10만 번째부터 써서 겹치지 않음 |
| ⑤ 평가 | KMMLU, HAE-RAE, MMLU 시험 문항 / 위키 다른 파일 | 3,008문항 | **①, ④에 절대 쓰지 않음** |

평가 문제(또는 같은 출처의 학습용 문제)를 칼질 기준에 넣으면 "시험 문제로 시험 공부"한 셈이 되어 결과를 믿을 수 없으므로 쓰지 않는다.

## 5. 단계별 방법

### 5.1 전문가 중요도 측정 (`scripts/01_calibrate.py`)

ERNIE 라우터는 64개 전체에 softmax를 한 확률 p에 보정값(bias)을 더해 상위 6개를 고르고, 고른 6개의 p를 합이 1이 되도록 다시 나눠 가중치 g로 쓴다. 보정 데이터 x가 지나갈 때 고른 전문가 j마다 다음을 기록한다.

| 기준 | 식 | 의미 |
|---|---|---|
| 빈도 | 전문가 j가 뽑힌 토큰 수 / 전체 토큰 수 | 얼마나 자주 쓰이나 |
| **REAP** (사용) | (1/뽑힌 토큰 수) × Σ g_j(x)·‖f_j(x)‖₂ | 뽑혔을 때 출력에 얼마나 크게 기여하나 (Cerebras REAP) |

- **재구성 검사:** 직접 계산한 Σ g·f + 공유 전문가 출력이 실제 모델 출력과 같은지 확인한다(상대오차 < 5%). 다르면 계산식이 틀린 것이므로 멈춘다.

### 5.2 칼질 (`scripts/02_prune.py`)

- MoE 층(1~27번)마다 REAP 점수 상위 K개(K = 48, 32)를 남긴다. 모든 층에서 K는 같다.
- 체크포인트 파일에서 남길 전문가만 골라 0번부터 다시 번호를 붙이고, 라우터 가중치와 보정값도 같은 전문가만 남긴다. GPU가 필요 없다.
- 라우터가 고른 전문가끼리 가중치를 다시 나누므로, 전문가를 지워도 가중치 계산 방식은 그대로다.
- 공유 전문가 2개와 0번 층 MLP는 건드리지 않는다.
- **검증:** 한 번도 선택되지 않는 전문가만 지우면 출력이 원본과 완전히 같아야 한다 (`tests/test_pipeline.py`).

### 5.3 양자화 (`scripts/03_make_gguf.py`)

llama.cpp로 GGUF 변환(Q8_0) 후 각 형식으로 다시 양자화한다. 모든 변형에 같은 절차를 쓴다.

| 형식 | 비트(대략) | 용도 |
|---|---|---|
| Q6_K | 6.6 | **기준 정밀도.** 거의 무손실이고 원본(약 18GB)도 L4에 들어가서 칼질 효과 비교에 사용 |
| Q4_K_M | 4.8 | 배포 형식. 원본도 이 형식으로 만들어 경제성 비교 |
| Q3_K_M | 3.9 | 양자화 비교 |
| Q2_K | 3.0 | 양자화 비교 |

### 5.4 한국어 LoRA (`scripts/04_train_lora.py`)

| 항목 | 값 |
|---|---|
| 대상 | ko-k32 (전문가 32개) |
| 데이터 | KULLM-v2 6,000개, ERNIE 채팅 형식, **답변 부분에만 손실** |
| LoRA 위치 | 어텐션 q/k/v/o, 공유 전문가·0번 층 MLP, 남은 라우팅 전문가 |
| 고정 | 라우터 (칼질로 정한 선택 구조 유지), 임베딩 |
| 설정 | r=16, α=32, 학습률 2e-4(cosine), 1에폭, 최대 1024토큰, 배치 2×8 |
| 이후 | LoRA를 합침 → GGUF → Q6_K / Q4_K_M |

### 5.5 평가 (`scripts/05_eval.py`)

| 평가 | 내용 | 문항 수 |
|---|---|---|
| KMMLU | 한국어 전문 지식 (45과목, 과목당 20문항) | 900 |
| HAE-RAE Bench 1.0 | 한국 문화·어휘·역사·독해 (전체) | 1,538 |
| MMLU | 영어 지식 (57과목, 과목당 10문항). 한국어로 바꾸며 영어를 얼마나 잃었나 참고 | 570 |
| 퍼플렉시티 | 한국어/영어 위키 (보정에 안 쓴 파일), 512토큰 × 200조각 | - |
| 생성 예시 | 에너지 분야 포함 한국어 질문 8개 (보고서에 직접 비교) | - |

**채점:** 채팅 형식으로 문제를 주고 답변 자리에 "정답:"까지 써 둔 뒤, 다음 토큰으로 보기 알파벳(A~E) 중 확률이 가장 높은 것을 답으로 본다. 모든 변형에 같은 방식을 쓰므로 **변형끼리 비교**하는 데 공정하다.

### 5.6 속도·전력 측정과 경제성 (`scripts/06_bench.py`, `scripts/07_econ.py`)

- **속도:** llama-bench로 프롬프트 처리(512토큰)와 생성(128토큰)을 따로 10번씩
- **전력:** nvidia-smi로 0.2초마다 기록하고, 모델 로딩처럼 GPU가 쉬는 구간을 뺀 연산 구간만 평균
- **메모리:** 파일 크기, 측정 중 최대 VRAM

| 지표 | 계산식 |
|---|---|
| 1000토큰 생성 에너지 (Wh) | 생성 중 평균 전력(W) ÷ 생성 속도(토큰/초) × 1000 ÷ 3600 |
| 100만 토큰 비용 (원) | GPU 시간당 가격 ÷ (생성 속도 × 3600) × 1,000,000 |
| 필요한 GPU | (파일 크기 + 1.5GB) 이상의 VRAM을 가진 가장 싼 GPU |

GPU 가격은 코랩 유닛 소모율($0.10/유닛)과 엘리스클라우드 요금으로 `configs/experiment.yaml`에서 계산한다.

**Qwen3.8-Flash-Next 확장:** 라우팅 전문가 약 121B, 나머지 본체 4B, n-gram 임베딩 51B, MTP 4B로 나누고, ERNIE에서 쓴 "남긴 전문가 비율"을 적용해 필요 메모리를 계산한다 (전문가 4.25비트, 나머지 8.5비트, n-gram 임베딩은 CPU 메모리, MTP 제외). 한국어 점수 변화는 ERNIE에서 측정한 값을 "예상치"로 함께 적는다.

## 9. 한계와 주의점

- 시드 하나로 한 번씩만 실험한다. 차이가 1~2%p 이내면 우연일 수 있다.
- 객관식 채점은 바로 답하게 하는 방식이라 실제 대화 성능과 다를 수 있다 (변형 간 비교용).
- 비용은 요청을 하나씩 처리하는 기준이라, 여러 요청을 묶어 처리하는 실제 서비스보다 비싸게 나온다.
- 어휘 확장은 새 토큰 임베딩을 위키 일부와 지시문 6천 개로만 학습하므로, 드물게 나오는 새 토큰은 충분히 배우지 못할 수 있다. 어휘를 더 늘리면(1만6천 개 -47%, 3만2천 개 -52%) 토큰은 더 줄지만 학습 데이터가 훨씬 많이 필요하다.
- 어휘가 다른 모델끼리는 토큰당 퍼플렉시티를 비교할 수 없어서, 같은 글 전체에 대한 글자당 비트(bpc)로 비교한다.
- Flash-Next 확장은 계산값이다. 구조가 달라 실제 성능 변화는 다를 수 있다.
